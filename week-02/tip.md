## Week 2 – Requirements Refinement, Collaboration Tools, and Retrospective

During Week 2, the team completed the Git/GitHub Recipes lab as required. This involved applying core version control practices, including cloning the repository, creating and working on branches, committing changes with clear and meaningful messages, pulling updates from the remote repository, and pushing changes back to GitHub.

I actively participated in this process by committing configuration-related updates and ensuring my local repository remained synchronised with the main branch. I also resolved minor merge issues when pulling changes from teammates. Completing this lab improved my confidence in using GitHub collaboratively and reinforced best practices for version control within a team-based software project.


My understanding of the client’s requirements continued to develop during Week 2 through further review of the project specification and discussions within the team. It became clearer that the client’s primary priority was a stable and reliable system that could successfully demonstrate end-to-end functionality during sprint reviews.

In particular, the client required a backend API that could reliably connect to a relational database and expose endpoints that the frontend could consume. This reinforced the importance of correct configuration and integration over additional features or visual refinement at this stage. I also gained a clearer understanding of how playground items, collections, variants, and images were expected to relate to each other within the system.

To support this understanding, a draft MoSCoW analysis was discussed within the team:

Must Have: Backend API setup, database connectivity, frontend–backend communication

Should Have: Basic item and collection display, image support

Could Have: Improved UI styling and additional filtering

Won’t Have (Sprint One): Advanced reporting and extended user management

This prioritisation helped align the team’s effort with client expectations for Sprint One.


Several tools and processes were put in place to support effective collaboration. GitHub was used as the central platform for version control and documentation, including the work diary and shared codebase. A consistent commit workflow was agreed to reduce conflicts and maintain clarity.

The team also maintained regular communication to ensure everyone was aligned on technical decisions, particularly around backend configuration and environment setup. I worked closely with my teammates to confirm that the backend was properly configured and that frontend API routes matched the backend endpoints. This collaborative approach helped reduce integration issues and ensured the team remained on the same page.


Reflecting on Week One, the main success was establishing a shared understanding of the system architecture and agreeing on the technology stack. The separation of frontend and backend responsibilities provided a clear structure for development.

However, some initial challenges were encountered due to unfamiliar technologies and configuration issues. These highlighted the need for clearer documentation and earlier testing of environment setups. As a result, the team agreed to improve communication around configuration changes and prioritise early integration testing moving forward.


During Week 2, a README.md file was created to provide a high-level overview of the MollyLimpets project. The README documents the purpose of the system, the chosen technology stack, key functional and non-functional requirements, and the focus of Sprint One. This ensures that both team members and stakeholders can quickly understand the project scope and development approach.
